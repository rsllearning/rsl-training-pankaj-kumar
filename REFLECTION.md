# Reflection on AI Productivity and TDD Guardrails

During this subscription pricing assignment, I used AI tools across all the development phases from writing initial tests to refactoring the service into Spring Boot. Working this way showed me both the good sides of AI speed and also why human oversight is still very much needed.

### Where AI Accelerated Development
The biggest advantage of AI was definitely speed and getting rid of boilerplate work. In task 1, it generated large JUnit 5 test suites with `@Nested` classes and `@ParameterizedTest` in just few seconds. That saved me a lot of typing for all the tier and tenure combinations. Later in task 4, it quickly scaffolded the Spring Boot structure, including Java 21 switch expressions, record classes for `PricingRequest` and `PricingResponse`, and controller setup. Also in task 5 when brainstorming edge cases, AI came up with interesting ideas that I didn't think of initially, like Cyrillic homoglyph characters in voucher codes (`SАVE20`) and zero-width spaces.

### Where AI Introduced Weak Logic
However, blindely trusting the AI output would have caused serious bugs. In task 1, the AI hallucinated the method signature and called `calculatePrice` instead of `calculateMonthlyPrice`, and even made up an imaginary two argument overload. 

Another big issue was context awareness. When prompted for security and validation tests, it started adding SQL injection (`' OR '1'='1`) and XSS payload tests which makes no sense for an in-memory math pricing service. Even worse, some assertions were totally weak and tautological, like checking if an exception message `contains(voucher) || !isBlank()`. This condition passed on basically any string and gave false confidence. It also missed the critical boundary months 12 and 36 in several test cases and wrote a fake floor check that tested $17.50 with a `>= 0` assertion.

### How TDD Prevented Technical Debt
This is where the strict TDD cycle really saved the project. Because we had to audit and fix the tests first in the RED phase, the tests became an exact specification before writing any implementation code. When I prompted AI for the green phase, having strict failing tests forced it to write only the minimal code needed instead of over-engineering things. 

Later when refactoring the whole codebase into separate packages and adding REST controller, having around 130 passing tests gave full confidence that no pricing logic was broken. Without TDD, the bad assumptions and shallow checks generated by AI would have slipped straight into production and created silent technical debt.
